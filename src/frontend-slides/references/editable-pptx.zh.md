# HTML → 可编辑 PPTX

对已有 HTML deck 需要一份 `.pptx` 副本时使用本分支。保留其内容、顺序与视觉方向；直接进入转换，不要重复简报或样式探索。同一份新 deck 若要求两种格式，则在创作前读本文件，然后走常规 HTML 生成流程。

这是一份操作参考，不是内置导出器。本技能不附带任何 HTML → PPTX 引擎、维护中的分叉或补丁集。[PPTX → HTML](pptx.md) 是另一个分支。

## 转换契约

**可编辑**意味着内容文本仍是原生文本，简单几何仍是原生形状/线条，且在对用户的编辑任务必要时，表格或图表仍是原生对象。照片与 logo 仍是图片。SVG 或 PNG 可以被移动和缩放，但不会因此让其文本或几何变得可编辑。

按以下顺序选择表示形式：

| 源内容 | 优先的 PPT 表示 |
| --- | --- |
| 标题、正文、图注、标签、数值 | 带字体/文本段样式的原生文本 |
| 卡片、纯色填充、边框、箭头、圆、坐标轴、连接线 | 原生形状/线条；多边形并不必然要求用截图 |
| 需要编辑数据的表格或图表 | 原生表格/图表，或就可编辑性更低的表示形式达成明确约定 |
| 照片与 logo | 作为图片嵌入原始素材；单独复现裁切/适配 |
| 无法合适映射到原生的复杂效果 | 带记录原因与可编辑性损失的局部回退 |

截图是回退手段，不是转换的证明。描边文本、SVG 文本或整页图片都不满足对可编辑内容的请求。在降级所需的可编辑内容或实质改变设计之前，取得用户同意。把许多原生形状组合起来，并不会把它们变成可编辑的数据图表。

## 1. 检查 deck 与工具

在选择工具之前，读 HTML、素材文件与运行时。记录幻灯片数量/顺序、创作舞台尺寸、字体/字重、图片、覆盖层/图注、表格/图表，以及交互内容预期的静态状态。确认用户需要编辑哪些对象；除非用户另作说明，都用上面的原生优先契约。

一个候选是 [Hasasasa/html-to-editable-pptx](https://github.com/Hasasasa/html-to-editable-pptx)，用于触发本工作流的转换案例。按实际使用的修订读它的 `SKILL.md`、依赖声明与 CLI 帮助。在任务报告中记录仓库/修订、命令/选项，以及任何已有的本地修改。移动的 `main` 不是可复现的版本。本链接是发现指引，并不认可其所有输出或上游工作流规则。

准备好其环境与导出副本后，该候选的基本调用是：

```text
python <converter-dir>/convert.py <deck>/index.pptx-source.html --out <deck>/index.pptx
```

使用前用 `python <converter-dir>/convert.py --help` 确认选项。任何自动创建/复用的审计副本都必须来自准备好的视图。保持校验开启；检查警告与证据，而不是把命令等同于验收。

检查所选实现本身，而不只是它宣称的 CSS 支持：

- `<img>` 是嵌入源字节，还是捕获其渲染框？内联 SVG 会变成原生对象、SVG 图片，还是 PNG？
- 哪些 CSS 模式会触发装饰截图？它们会捕获图注、兄弟元素或祖先背景吗？
- 舞台变换、字体字重、空装饰元素与形状主题效果是如何处理的？
- 它能否遵守 deck 的导出状态，并为视觉保真度与可编辑性两者都产出证据？

在完整运行之前，按需检查 Python/Node、浏览器启动、字体与 PPTX 渲染器。渲染需要可用的 Office/LibreOffice 路径；LibreOffice → PDF → PNG 流程可能还需要 Poppler。缺包时使用项目自身的环境机制并取得必要同意；在 Nix 上使用声明式项目配置，而不是命令式系统安装。仅当转换器支持时才复用系统浏览器。

把工具代码与 deck 分开，避免写入只读的已安装技能。使用受支持的设置，把允许的缓存/配置放在可写任务目录中。安装字体及其他用户/系统改动需要同意。嵌入字体不能证明每个查看器都会使用它；检查嵌入权限与渲染器可用字体。

完成条件：deck 清单、编辑需求、工具身份、转换命令与可用渲染器均已确定。若依赖或工具能力阻碍请求，说明阻碍，而不是承诺导出。

## 2. 准备导出视图

保留原始 HTML 与素材。把仅用于转换的改动施加到同级工作副本上，以便相对素材仍能解析；记录与源文件的偏差。在转换刚编辑过的源文件之前，检查所选转换器是否会自动复用旧的工作副本。

使用[既有导出契约](../html-template.md#export-contract)：加载 `?export=1`，等待 `window.deck.ready`，并用 `window.deck.goToSlide(index)` 激活每一页。检查动态组件在其最终静态状态下的表现。较旧的 deck 需要等效的显式准备步骤。若转换器忽略此契约，就使用有文档的适配器/准备设施或准备好的副本；给无关的截图运行加一个查询串并不会改变转换器的输入。

导出视图排除编辑开关、导航控件、对话框与不属于幻灯片内容的工具提示。把浏览器编辑器保留在原始 deck 中。验证实际转换视图，而不只是另外打开的浏览器标签页。

保持单一坐标空间：把实测的视口坐标换算回创作舞台坐标恰好一次，计入缩放与平移，或直接在单位尺度下测量舞台。把变换后的 `getBoundingClientRect()` 边界与计算出的 CSS 值（例如 `font-size`）区分开，后者可能已经处于创作单位。检查已知的文本/图片边界、裁切矩形、字号与幻灯片尺寸的单位是否一致，而不是不加区分地施加逆缩放。改 CSS 宽度无法修复混用坐标空间的转换器。

对于双格式创作，在设计允许时优先为简单图表使用显式几何与本地素材引用。保留所选设计，而不是禁止每个 HTML deck 使用渐变或阴影。

完成条件：准备好的视图具有正确的幻灯片数量、无编辑器界面、字体/媒体/组件已稳定，且舞台坐标映射一致。

## 3. 在代表性页面上证明路线

在转换整个 deck 之前，测试覆盖其实际风险的页面：密集 CJK 文本、混合字重、带重叠图注的照片、图表/表格，或复杂装饰。若工具无法选择页面，就转换一个临时子集。

同时检查渲染出的 PPTX 与其对象结构。把每个必需元素归类为原生文本、形状/线条、表格/图表、源图片或回退图片。从嵌入媒体与关联关系确认源图片复用，而不是凭是否存在 `<img>` 标签。未改动的原始素材可用哈希比对；若工具重新编码了素材，记录这一点并检查尺寸、裁切与质量，而不是声称逐字节复用。

独立于形状计数检查文本：截图下的隐藏文本与图片内部重复的图注会让计数看起来健康。整页照片在它是源背景时是正当的；整页都是合成幻灯片图片则不是同一回事。

若试点失败，使用[基于症状的排障](pptx-troubleshooting.md)区分导出准备、坐标错误、工具缺陷、渲染器行为与真实的格式限制。在把失败扩展到每一页之前，选择另一条路线或就可接受的有限妥协达成一致。

完成条件：本 deck 所需的每种表示形式都有证据，且任何提议的可编辑性损失或实质设计改动都已获接受。

## 4. 转换与修复

对准备好的副本执行完整转换。保存命令、警告、对象/回退清单，以及 HTML/PPT 对比渲染。产出了文件或成功退出都不是验收；有些转换器在字体解析、渲染或审计生成失败后仍会继续。

对每条发现，记录页面、稳定元素名称、HTML 状态、PPT 差异、疑似输出通道与支撑证据。批量处理相关修复，重建，并检查被改动的页面以及可能的回归。

- 页面局部改动只有在缓存有效性确立后才可以只做增量转换。
- 全局 CSS、字体、导出准备、转换器选项/代码或页序改动会使受影响的缓存证据失效；重建/复审所有可能受影响的页面。受影响集合不确定时，做完整运行。
- 反复出现的发现需要有针对性的探针与诊断，而不是无休止的 CSS 猜测，或自动接受为格式限制。按需检查测量值、输出 XML 与工具行为。
- 工具缺陷不是 HTML 反模式，也不是 OOXML 限制。不要把任务变成转换器维护：尝试受支持的路线、另一个工具，或约定好的变通方案。若都无法满足请求，报告阻碍；维护补丁/分叉是另一项工作。

在验收之前保留审计摘要与证据。只能在约定的清理范围内删除体积庞大的中间文件；保留最终发现、工具身份与回退清单。

## 5. 双轴验收

### 视觉保真度

在共同宽高比/尺度下渲染最终 PPTX，并与准备好的 HTML 逐页比对。留意缺失对象、错误的尺寸/裁切、背景污染、重复图注、被裁切文本、字体/字重/换行变化、层叠顺序与意外的主题阴影。缩略图拼版有助于初筛；在否定疑似缺陷之前检查细节页面。

需要时使用有图像能力的 agent 做视觉检查，并在派遣整 deck 审计之前确认它确实能查看图片。若运行时不提供视觉，请人类检查。仅生成对比图片不构成检查。

### 可编辑性与完整性

按清单检查每一页的 PPTX 结构：内容文本是原生文本，所需几何是原生，所需表格/图表是承诺的对象类型，图片解析到预期素材，且每个回退都有原因。检查隐藏重复与合成幻灯片截图。文本抽取与 XML/对象计数是支撑证据，不是完整通过。

在目标演示应用中测试代表性编辑：改文本、移动/缩放形状，并在需要时编辑表格/图表数据。若该应用不可用，把结构检查与应用层编辑未验证区分开。LibreOffice 渲染不能确立 PowerPoint 或 WPS 兼容性。

完成条件：双轴都有与最终构建绑定的证据；剩余缺陷与验证缺口已明示，且任何必需的妥协都已获用户同意。若无渲染器可用，询问是安装/使用一个、把验证移到别处，还是交付一份明确未验证的草稿。绝不要把那份草稿称为视觉已批准。

## 6. 交付

报告：

- PPTX 路径与幻灯片数量；源 HTML 未改动；若保留则给出准备好的副本路径。
- 工具修订、调用方式，以及用于检查的渲染器/应用。
- 哪些仍是原生、哪些复用了源素材，以及哪些页面/元素被栅格化、描边、重新编码或做了视觉简化，以及原因。
- 视觉覆盖、结构覆盖、应用编辑测试，以及所有未完成的检查/缺陷。
- 最终审计摘要与任何保留证据的路径。

使用精确表述，例如“正文与卡片形状是原生；两个装饰性标签是图片”。把“完全可编辑”留给有证据的约定范围。仅一次干净视觉评审不能支撑该说法。

## 依据与限制

本工作流提炼自一个 36 页的 HTML → PPTX 案例：截图背景污染、图注被烙进图片后又作为文本重复出现、编辑器界面泄漏、缺失简单几何、字体/坐标不匹配，以及继承的主题阴影。那次对话的最终成功报告不是经验证的基准，其本地补丁也不在此交付。把这些当作需要复现的回归场景，而不是关于一个仍在演进的转换器的永久事实。要了解当前症状与需收集的证据，读 [PPTX 排障](pptx-troubleshooting.md)。
该案例中的若干 SVG 变通做法通过变成图片改善了外观；它们促成了独立的可编辑性门禁，而不是承诺 SVG 可编辑转换。
