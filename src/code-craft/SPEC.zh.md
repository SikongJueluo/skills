# code-craft

在有证据的前提下直接满足当前需求来写代码。**不要把自己的不确定性转化为运行时复杂性。**

质量门槛是 [references/standards.md](references/standards.md)。首次编辑前先读它；本页是工作流程。

## 1. 确立本地契约

读取项目规则（AGENTS.md、CLAUDE.md、docs、lint、tests）以及你即将改动的代码。对每一个会影响实现的接口，找到其保证：声明、实现、边界校验、测试、文档。调用方展示的是用法，而不是保证。

调查到决策已确定为止，而不是到仓库已被理解为止。当某个问题仍未解决时，报告该未知项，而不是选定一个契约再为它做防御。

完成标准：对你依赖或守卫的每个保证，你都能说出其来源；会改变行为的未决问题已被陈述，而不是用代码绕过。

## 2. 实现当前需求

在标准之下，写出满足任务的最简单的直接实现。任何新的守卫、默认值、重试、包装、配置或分层都需要一个它所服务的事实。让错误通过项目既有的机制传播，除非这段代码自身负责恢复。

把判断放在代码形态里，而不是放在说明报告或设计笔记里。

完成标准：每个新增分支与抽象都有当前的理由，diff 中不含该需求不需要的任何东西。

## 3. 精简与验证

重读自己的 diff，找出那些为了满足不确定性而非需求而添加的代码。优先选择更清晰的形态，而不是更短的形态。运行项目要求的检查（format、lint、typecheck、tests），并知晓其结果。

完成标准：这个 diff 是你在评审中愿意为之辩护的，且验证结果已知，或已报告其缺失。
