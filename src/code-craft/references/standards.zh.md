# 代码工艺标准

`code-craft`（写代码）与 `code-craft-review`（评审代码）共用的质量门槛。两者都把它应用到手上的改动上。

目标不是更少的行数。而是让读者为了信任这段代码而必须承载的概念、假设与隐藏失效模式更少。一个分支、默认值、重试、包装或分层，靠服务于当前需求的某个事实或真实的系统边界来挣得位置——而不是靠作者知识上的空白。

## 先有证据，再写代码

| 不确定性 | 示例 | 应对 |
|---|---|---|
| 系统行为：存在真实失效模式 | 网络中断、畸形的外部载荷、文件缺失、并发写入者 | 在边界处处理它 |
| 作者知识：契约尚未核实 | “也许 `getUser()` 返回 null” | 读定义、实现与测试；不要为疑虑写代码 |

- **不要把自己的不确定性转化为运行时复杂性。** 如果你说不出某个守卫服务的失败场景及其后果，你还没准备好写这个守卫。
- 按此顺序寻找契约：确立该保证的声明与实现；数据进入处的校验；钉住该行为的测试；说明意图的文档与 ADR。调用方展示用法，而不是保证。
- 注释、TODO 以及提交或 PR 描述是对代码的主张，而非代码行为的证据。一段解释“守卫为何存在”的注释，并不确立“该守卫是必要的”。
- 信任同一信任域内已经确立的保证——即共享相同校验与不变量的代码。已确立意味着你能指出强制该不变量的代码或测试；仅有名称、docstring 或约定只是线索。在数据跨越进入新域处校验它：网络、磁盘、用户输入、子进程、反序列化的载荷、硬件。
- 决策已确定时就停止调查，而不是仓库已被理解时才停止。当某个会改变行为的问题仍未解决时，报告那个具体的未知项，而不是用代码绕过它。
- 门槛是对称的。删除守卫同样需要证据：一个契约、一个通过断言该行为来钉住保证的测试，或一个覆盖同一需求的更简单实现。一个仅仅避开该场景的测试什么也证明不了，而缺少测试或缺少调用方对可达性什么也说明不了。

## 1. 契约

- 依赖最窄的已陈述保证。在拥有该不变量的边界处校验一次；不要在每一跳重复同一校验。
- 类型与转换描述的是形状，不是运行时真相。外部载荷在解析它的代码完成校验之前都属于未校验数据。
- 当文档与代码冲突时，报告该冲突：行为是调用方实际得到的东西，而文档可能陈述的是意图中的契约。不要静默选择更能为更多代码辩护的那一侧。
- 重复校验测试：当同一路径已确立该保证、且两点之间没有新的信任边界时，新的校验就是冗余的。
- 一个可从任何缺少该校验的路径到达的函数，拥有自己的校验。只有当每条入口路径都已确立该保证时，某次校验才算重复。

## 2. 错误处理

- 处理失败前先分类：正常缺失（查找未命中、空查询）、可恢复失败（有界策略重试、语义已定义的降级）、程序员错误（快速而响亮地失败）。
- 一个处理器只做一件已陈述的事：恢复、翻译、补充上下文，或继续向上传播。仅为让程序继续运行而选择的默认值，会把失败变成虚假的成功。
- 当本次改动能触达失败源头时，在源头修复它。让系统看起来健康的降级默认值处理的是症状，不是病因。
- 正常缺失应映射到代码能识别的具体结果：缺失的目录变成空列表。而一个同时吞掉意外失败的兜底默认值不是那个结果。
- 如果该失败对调用方看起来会与正常空结果完全一样，就暴露差异，或明确决定它们就是同一结果。
- 保持原始失败可见：串联原因、在决策点记录、重新抛出。抹去具体错误的泛化信息不是处理。
- 当这段代码不负责恢复时，使用项目既有的传播机制：异常、`Result`、错误边界，或记录并重抛。
- 这些是边界职责，而非过度防御：外部输入校验、资源清理、事务回滚、并发与生命周期守卫。保持它们准确，而不是为了简化而删除。

## 3. 控制流

- 主路径自上而下可读。每个分支条件都映射到一个不同的真实场景：需求、契约或已确认的失败。
- 优先清晰的序列，而不是省下几行却多出一个命名概念的压缩表达式。概念才是度量，行数不是。
- 前置条件的提前退出没问题。嵌套深度是症状，而非规则；缺陷在于不必要或不可达的分支。
- 每项校验与每次状态迁移只保留一个所有者。可能对同一状态给出矛盾结论的并行标志位或布尔值是等着发生的 bug。

## 4. 命名与数据

- 使用项目的领域词汇。一个概念在整次改动中保持一个名称。
- 一个名称应能在调用处不依赖实现地读懂。`result`、`data`、`tmp`、`handle`、`manager` 通常没有说出类型没说出的任何东西。
- 表示领域实际拥有的状态。布尔参数与字符串化的模式隐藏状态；当项目有命名类型或枚举时就用它。
- 返回调用方需要的东西，而不是并行出参或哨兵值。
- 命名与结构方面的结论仍然需要具体的成本：读者或调用方会误读什么。个人偏好不是结论。

## 5. 局部抽象

- 抽象必须隐藏一个决策、命名一个概念，或集中重复的真实工作。没有增加意义的转发是成本，不是分层。
- 只有一处调用点不是缺陷。单次使用的辅助函数在以下情况挣得位置：它命名了一个调用处本会重复推导的领域概念，或让调用方保持可读；当第二个真实变体出现时再泛化。
- 配置、开关、适配器与兼容分支需要当前存在的、有名字的变体。“以后可能要用”不算。
- 删除测试：删掉该抽象，重读调用处。如果调用处更清晰，该抽象没有职责；如果一个真实概念变得无名，就保留它。
- 泄漏其实现的抽象——调用方必须了解内部才能使用——不是在隐藏复杂性。

## 6. 改动范围

- 实现眼前的需求。新的公开参数、扩展点、迁移与无关重构等待一个需求。
- 只有当本次改动没有它就无法正确时，才修复邻近缺陷；否则报告它。
- 兼容性需要一个已发布或已请求的契约。在移除已发布行为前查看项目策略，且不要为不存在的未来发明一个。
- diff 不是用来展示周密性的地方。无关的清理让改动更难评审、更难回滚。

## 注释

项目规则优先：注释策略、lint、豁免登记表或归属规则就是当地法律。项目没有时，以下是默认。

- 不添加普通的解释性注释：不在函数体内、不在单条语句上、也不用来说明控制流。代码、类型、测试与下述 docstring 承载解释。
- 允许简短的模块、类与函数 docstring 或声明文档，但不要求，且它们是唯一的散文渠道。只有上限，没有配额：模块或文件头 5 行内容，类或函数 3 行。在没有 docstring 的语言中，对文件或声明的文档注释施加同样的界限。
- docstring 陈述签名无法表达的契约：单位或坐标系、归属与生命周期、外部格式、读者无法从代码或测试重建的约束，或为何显而易见的替代方案是错的。它不叙述实现。
- 长的设计历史与实验笔记留在代码之外；当项目有 docs 位置时，指向那里。
- 保持注释为真：修复或删除被本次改动变为假的注释。不要批量删除历史注释。
- 工具指令、许可证头、linter 抑制、生成标记、类型检查器 pragma 与关联 issue 的 TODO 标记不是解释性注释；只在工具或项目要求时使用它们。
- 不要通过把同一解释搬到 Markdown、断言、另一个文件的注释、辅助函数名字或长标识符里来满足 docstring 界限。
