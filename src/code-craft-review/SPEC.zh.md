# /code-craft-review

评审**代码**，不评审计划、架构，也不评审该改动是否应合并。门槛是 [../code-craft/references/standards.md](../code-craft/references/standards.md)，从本 skill 所在目录解析；在判断任何事之前先读那个文件。只读标准，不读 `code-craft` 流程。若标准文件缺失，报告 `code-craft` 未安装并停止。

## 范围

在阅读代码前先固定目标：

- 使用用户点名的 diff、revset、文件或 PR。
- 否则评审当前工作副本的 diff；若为空，则评审该分支与其默认分支 merge base 的差异。
- 说明基线与范围内含。在 Jujutsu 仓库中，用 `jj log`/`jj diff` 解析它，并遵循 `jujutsu` skill；不要用裸 git。
- 完整读取每个被改动文件，以及判断它所需的相邻代码；不要审计整个仓库。若 diff 为空，说明没有可评审内容并停止。若无法获得任何基线，询问一次。

**只读。** 任何时候都不要编辑、格式化或修复，除非用户明确要求修复；该要求会把你切换到 `code-craft`，随后在该门槛下遵循它的流程。

这是代码质量结论。它不是合并门禁，不是架构裁决，也不是全系统验证报告；这些请用 `arch-code-review`。

## 如何评审

1. 阅读 diff 与每个被改动文件。用需求与提交描述判断意图，用代码与测试判断行为。对每个新增的守卫、默认值、重试、包装、配置、兼容分支或抽象，寻找它所服务的事实：一个契约、边界校验、一个测试、一条已确认的失败路径，或该任务。对每个被移除的守卫或边界，找出现在覆盖同一需求的东西。把新增注释与注释默认规则对照检查，并把它们视为对代码的主张，而非代码的证据。
2. 当你找不到该事实时，先调查再下结论：接口背后的定义与实现、钉住它的测试、调用方、项目文档。模式匹配（`catch`、`??`、一个默认值、一个辅助函数）只是提示去看，不是结论。
3. 应用对称证据规则。要求删除需要：一个契约、一个通过断言该行为来钉住保证的测试，或一个覆盖同一需求的更简单实现。要求新增需要：一个已确认的外部边界或代码目前处理不当的失败路径。
4. 只报告会改变行为或理解的内容。每条结论都需要位置、证据、具体成本与最小方向。不打分、不列维度清单、不凑结论数量、不做泛泛称赞。
5. 仅当某个影响行为的判断需要确认时，才运行项目已有的低成本检查。检查通过不能为隐藏失败的代码开脱；与本次改动无关的检查失败是备注，不是结论。

优先更小的修复：移除冗余守卫、修源头而不是遮盖它、直接使用已确立的契约、澄清名称或数据形状，或折叠掉没有独立职责的分层。只为已确认的失败路径或需求添加代码。

## 输出

陈述范围与基线，然后给出以下之一：

**无需代码质量改动。** 改动后的代码符合门槛。点出你无法核实的任何假设。

**需要返工。** 按成本排序结论。对每条给出：

- `path:line` 或符号
- **证据**：代码做了什么，以及它与哪个契约、需求或失败路径相矛盾
- **成本**：具体后果——隐藏的失败、含混的状态、读者必须承载的概念、误导性的调用点
- **方向**：在满足当前需求前提下最小的改动；描述它，不要重写文件

**证据不足。** 点名确切未决项以及什么能解决它们：文件、文档或运行时事实。不要把猜测当作裁决呈现。

当结论与未决项同时存在时，两者都报告；结论仍然是可执行的。

如果代码没问题，就说明并停止。
