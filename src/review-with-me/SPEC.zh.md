# /review-with-me

准备一次**人类代码评审**，而不是又一份 agent 发现报告。Agent 调查整个改动，然后把承重代码连同足够上下文一起摆到人面前，使其无需在仓库里来回跳转就能做出判断。

本 skill 记录人的判断；它不给出合并结论。

## 范围

接受自然语言范围、提交 ID、分支/书签或 revset。精确解析它并复述：

- VCS
- 规范化后的范围
- 是否包含工作副本
- 被评审的净效果

当 `.jj/` 存在时，以 Jujutsu 为真理来源并遵循 `jujutsu` skill；否则使用 Git。解析有歧义时请人确认。若未提供范围，询问一次并给出可能的范围作为快捷选项。

版本 1 评审连续范围，在被要求时包含工作副本。对于离散的提交集合，请人选择拆分评审或给出连续边界。优先评审最终净效果；只在需要还原意图或定位改动时才检查提交演进。

范围限定的是被判断的对象，而不是证据可以来自哪里。阅读相关的既有代码、测试、文档、调用方与提交描述，但只报告由该范围引入、暴露或改变的事项。

## 规划评审

理解每一处实质行为与边界，把这些视角当作提示而不是固定清单：

- 数据结构、状态与契约
- 数据流、状态转换与生命周期
- 算法、控制流与失败路径
- 外部接口、系统边界与副作用
- 整体风险与遗漏

只选择有助于解释本次改动的视角，并按理解依赖排序。对宽泛或不熟悉的改动，在 slice 之前先给人一张简短的评审地图；对聚焦的改动，简短导览可直接进入第一个 slice。只在某视角的缺席本身是有用证据时才提及它，不要把它当作记账。

## 构建评审 slice

在选定的评审路径内，挑出**人的独立阅读具有价值的承重代码**，尤其是：

- 领域策略与用户可见行为
- 控制流、失败处理与不可逆效果
- 归属关系、生命周期与信任边界
- 塑造未来改动的公开契约与抽象
- 令人意外的实现选择或假设
- agent 发现的有后果的问题

把每项选择呈现为三类评审 slice 之一：

- **Verify** — agent 认为它是可靠的；人独立核验关键实现。
- **Problem** — agent 发现了有后果的问题；人在证据旁看到该主张。
- **Decision** — 正确性取决于意图、品味、本地知识、权衡或责任归属。

折叠机械改动、重复、生成代码，以及不承载行为或边界的本地声明。定义契约的声明或数据形状是承重的，不是机械的。任何包含非机械改动的范围都必须至少产出一个 slice。只有当整个范围都是机械改动时才允许零 slice，且回应必须解释原因。

## 让每个 slice 自包含

使用这个紧凑形状，需要时可调整标签：

````markdown
### [Verify | Problem | Decision] <这段代码控制什么>

**What happens:** <这段代码实现的行为，用平实的话说>
**Why it matters:** <如果它错了，代价是什么>

```<language>
<有后果的代码的短摘录>
// REVIEW ①
```

**Review:** <要人检查或决定的具体事项>
**Agent take:** <回答> — <具体成因或失败场景>
Source: `<path:start-end>`

① <对被标记的行或分支的详细解释，放在代码块下方>
````

保持代码块简短。用 `// REVIEW ①` 这类裸编号标记有后果的行，并把每处详细解释放在代码块下方对应编号处。优先让标记独占一行；只有在不会加宽摘录时才把它移到行尾。只有在结果语义完全一致时才为展示重新换行或调整缩进摘录，并说明这一点；Source 位置仍指向真实位置。

在回应中直接引用代码。只给引用副本加 `REVIEW` 标记，绝不给项目文件加。保留足够的周边控制流、输入与结果，使问题可被回答。跨文件流程在一个 slice 内用几段短代码块呈现，追踪 输入 → 变换 → 输出 或副作用，每段携带自己的标记；掩盖契约的合并摘录比三段小摘录更糟。源位置支撑 slice——它永远不能替代展示代码。

坦率暴露不确定性。没有可靠 agent 判断时直接说明。只纳入会改变判断的重大后果或未知项。

## 为不熟悉的读者解释

默认人能够流畅阅读这门语言，但不了解该模块或其领域；四个平实字段就是为这样的读者准备的。

- 模块或领域术语首次出现时就地解释；不要把人打发到别处查词汇。
- 把 What happens 写成代码实现的行为，而不是它相似的模式名称。
- 把 Agent take 落在具体成因与失败场景上——什么会坏、沿哪条路径坏——绝不复述抽象名词。
- 对数据流 slice，显式陈述 输入 → 处理 → 输出/副作用 的追踪，而不是只通过代码块隐式传达。
- 对复杂算法，用真实数值走一个具体的分步示例，而不是抽象描述步骤。

当人表示对该模块或该关注点已经熟悉时，该 slice 的字段就写得更简短，并按需再展开。教学范围限于评审该 slice——够做出判断，而不是通识课。

## 执行人类评审

以简短导览开场：该范围改变了什么、其可观察行为、代码无法确认的假设，以及 agent 检查了什么。在能降低认知负担时使用轮次，而不是为满足固定仪式。

- 保持每轮连贯。它可以沿一个视角或组合紧密耦合的视角，也可以包含人能够一起合理判断的任意数量 slice。
- 在人需要做出判断、下一处材料依赖该判断，或回应将变得难以评审时暂停。否则继续，不要发明检查点。
- 当仍有工作时，以简短结论收尾并说明接下来是什么。只有在多轮或延后的决定使进度不清时才使用进度台账。
- 接受自然回应：看起来对、担忧已确认、换一种选择、多解释些、查看更多上下文，或延后。
- 一旦有后果的问题变重要就立即提出，然后围绕人的回应重塑剩余评审。
- 每次回应后重新计算剩余评审；前提改变可能重新打开 slice 或重排路径。

把 agent 的有后果发现整合进 **Problem** slice，而不是放进独立的发现清单。只在 slice 之外概述这些：

- 已修复并核验的机械问题
- 授权状态与所需动作；任何有后果的问题本身仍出现在 Problem slice 中
- 由一个 slice 代表的重复实例
- 被折叠的材料，按原因与数量

只在人要求更宽泛的视觉检查、且 Plannotator 能精确展示规范化范围时才使用它；无法做到时说明该限制。

## 收尾

维护一份简短的已评审 slice 记录：

- 已接受的实现
- 已确认的问题与所需改动
- 人的决定
- 已接受或延后的风险，包括它们阻塞什么

当代码变动时，重跑相关检查、评审产生的净效果，并重新打开前提已改变的 slice。当范围边界变化时重新规范范围。

当每一处实质行为或边界都由某个已评审 slice 或明确的机械折叠类别代表；每个非机械范围至少有一个 slice；每个 slice 都已被接受、被改向或被延后；所需的 agent 工作已处理或记录；且范围仍然有效时，评审即完成。若某项判断形成持久的架构约束、公开 API 承诺、已接受风险或维护权衡，在结尾询问一次是否要把它固化到 issue 或文档中。
