# refactor-ui

根据用户的不满意意见修订现有视觉产物。现有产物是起点，用户反馈是任务说明。好的修改应当小而有依据，并保留用户已经认可的内容。

适用于值得保留的既有网页、应用界面、组件、幻灯片、文档布局或视觉模型。若要制作全新产物或方向尚未确定，先用小型原型探索。若要生成或转换演示文稿，由 `frontend-slides` 负责制作；本技能只处理针对现有演示文稿的反馈式修订。若用户只问哪里有问题，则检查并报告，不要编辑。

## 操作规则

- **先保留，再改进。** 指出用户已认可的方向、配色、字体、内容、交互和先前决定；除非意见明确针对它们，否则视为固定要求。
- **保留信息，重选表达。** 保留事实、含义、能力和必要署名。只要原有信息和操作仍可获取，就可以合并、移动或替换承载它们的卡片、图表和文案。
- **改变含义前先询问。** 删除独立论点、改变主张或移除能力都需确认；重复内容、迁移和压缩无需确认。
- **一次处理一组相关原因。** 修复证据支持的原因，其他呈现区域保持不动。
- **先取证再下结论。** 在同尺寸、同状态下渲染并比较。只看代码或干净的截图，不能证明反馈所指问题已经解决。
- **审美由用户决定。** 给出有理由的建议，但不要把偏好说成缺陷，也不要把推断写成项目规则。除非用户采纳，否则不要新增设计文档或惯例。

## 1. 界定问题

用用户自己的措辞重述不满意之处，然后检查产物、资源、项目设计规则，以及此前的反馈和认可。按用户实际看到的尺寸和状态渲染或打开产物并记录基线；使用产物已有的预览或截图流程。对整体缩放的固定舞台演示文稿，设计尺寸与截图尺寸并不相同；关键是前后使用同一视口。若产物使用图像作为证据，先打开图像，描述实际内容，再评判布局。若无法查看图像，委派给能查看图像的助手或如实报告未验证；不能只凭文件名或替代文字声称已检查。

写下需要保留的部分：必须延续的设计决定、内容和行为。将硬约束（已批准决定、项目规则、必需事实）与软偏好及自身推断区分开。硬约束需要用户来改变；软偏好用于指导选择。用户已认可的方向或项目惯例优先于本技能的默认做法。若没有项目规则或先前决定，就把产物自身的设计 token、组件和重复处理方式视为它现有的系统，并将推断规则保持为暂定结论。

完成条件：用用户措辞写出的一句话问题；存在基线（截图，或已检查的确切状态和来源）；保留清单已写下；任务类型已明确。

## 2. 建立可验证的假设

把感受与原因分开。“太杂”是一种感受；“三个区块都在争夺第一视觉焦点”才是原因。有效原因应指出某个元素及其作用机制。

列出 2–4 个候选原因，再收集能区分它们的证据：渲染结果、源文件、测量数据、文案、其他位置中的同类内容，以及产物用途。阅读当前原因分支会用到的参考文件，通常一两个即可。如果证据与参考文件中的默认建议矛盾，遵循证据并说明原因。若产物无法区分两个合理原因，且对应修复差异重大，则提出一个聚焦问题或展示一个小型变体；否则先尝试更小、可逆的改动。

若原因在内容逻辑、交互流程或产品本身，应当明确指出。只把问题藏起来的视觉改动不算修复。

把假设写成 **原因 → 改动 → 信号**：是什么导致了反馈、打算如何改，以及什么可观察结果能说明问题有所改善。

- 弱：“文字太多，删掉 30%。”
- 可验证：“说明段落和讲者提示重复了标题与结论已经表达的主张。将两者移到讲者备注中。信号：幻灯片只呈现一种收尾方式，观众仍能说出核心主张。”

### 太多、杂乱、密集或冗长

检查哪些内容、容器或图形在重复同一信息或争夺注意力，以及它们是否占错了层级。读[密度与呈现层级](references/surface.md)和[强调](references/emphasis.md)。

### 看不出重点、找不到第一眼该看哪里

检查焦点、层级、分组和标签。读[视觉表面](references/surface.md)和[视觉细节](references/craft.md)。

### 不一致、标题或标签漂移

检查同一角色的表达规则、锚点位置和 token 漂移。读[一致性](references/consistency.md)。

### 设计过度、装饰抢眼或“像 AI 做的”

检查叠加的强调、无用途的装饰和焦点竞争。读[强调](references/emphasis.md)。

### 廉价感、未完成、单调或普通

检查字体、颜色、间距、层次和图像。读[视觉细节](references/craft.md)。

### 难用、找不到操作或步骤太多

检查可供性、显著性、流程和渐进披露。读[交互操作的显著性](references/surface.md)。

### “感觉不对”或混合反馈

先确认产物的用途和第一视觉焦点，再查看证据最强的两个候选原因所对应的参考文件。

### 完成条件

有一个包含原因、改动和信号的工作假设；其他候选原因已说明并排除或暂缓；每个已读参考文件都由当前原因触发。若任务仅要求分析，到此停止，报告诊断和建议改动，不要编辑。

## 3. 选择干预方式

选择能改变已命名信号的最小改动组合。优先用结构和字体建立层级。只重复已有信息的视觉元素，可以合并或移除；承载独立信息的元素，可换一种表达或移到合适的层级。保留一个有辨识度的元素；克制不等于抹平。每次删减都应有具体理由，而不是为了凑比例。当证据指向分组或结构而非表面样式时，重组或提出结构性改动。当问题涉及产品交互模型时，说明单纯视觉调整无法解决。不要仅因改动较大就退回到探索阶段。

当选择确实属于用户时，行动前先确认：存在两种或更多实质不同的审美方向；一个独立论点或主张会消失；一项能力会被移除；或整体方向将改变。只要原有区别仍然清晰，改变视觉编码方式本身属于设计调整，不算内容改动；只有当该编码是唯一的信息载体，或用户依赖该编码时才需要确认。若原因和修复方式都清楚，直接行动。若用户反对的是方向而非执行，说明这一点并给出两三个替代方案，不要继续打磨已被否定的方向。不要重问你能从产物中检查到的事实，也不要重问用户已经给出的反馈。

完成条件：改动列表范围明确，并映射到各个原因；保留清单仍完整；涉及含义或方向的选择已经确认。

## 4. 编辑

在产物自身的系统内工作：现有 token、组件、字体层级、间距节奏、布局规则和运行时。把内容移到适当层级，例如讲者备注、帮助信息、详情页或次级面板，不要硬塞到主呈现区域。

不要引入新的视觉语言、重设相邻界面样式，或修复反馈未涉及的内容。删除此次改动遗留的 CSS、类名和资源；其他内容保持不动。对交互界面，保留行为、状态、键盘访问、焦点、标签及错误恢复。

完成条件：差异仅涉及被反馈的问题表面及其直接依赖；每个被移动或删除的区块都在其他层级得到交代，或明确视为有意移除。

## 5. 对照反馈验证

按与基线相同的状态和尺寸重新渲染并比较。依次检查：

1. **原始信号。** 假设指出的现象，例如收尾方式变成一种、第一视觉焦点明确，或标题角色可预测。
2. **表达。** 新读者仍能说出要点；改动涉及的主张有产物内容支持，包括图像、数字、说明和示例。
3. **回归。** 布局、溢出、裁切、交互、导航、无障碍及相邻界面保持不变或有所改善。
4. **残余问题。** 仍未解决、主观或无法验证的事项，例如没有渲染器、浏览器或必要状态，或审美判断仍待用户决定。

若无法渲染，说明哪些检查仅基于源文件。程序化测量（像素数、元素数、溢出、颜色直方图）只能作为辅助证据，不能代替视觉判断。若无法查看产物，应将视觉检查委派给具备视觉能力的助手、报告为未验证，或询问用户；不要仅凭代理指标声称视觉效果改善。若图像或示例承载的主张无法核实，明确指出具体哪一项未经验证，不要将其重复为事实。

完成条件：针对已命名信号有修改前后证据；已完成回归检查；明确列出仍未验证的内容。

## 6. 汇报

先说明改了什么以及原因。展示与已命名信号相关的修改前后证据，并重申保留清单。只询问证据无法决定的审美选择。不要在验证范围之外宣称设计已“修好”或“更好”，也不要给审美打分或作通过/失败判定。若用户仍不满意，应修订假设，而不是为其辩护。

完成条件：用户看得出改动、已验证内容及仍由用户判断的事项。
