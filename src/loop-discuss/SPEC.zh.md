# loop-discuss

## 哲学

终点的边界往往藏匿于未知，试图一步到位，画完整圆往往会踩空；而每次只画一个完整的小圆，看似绕远路，却能让每一步都落到实处，顺手照亮前往下一圈的路。

## 内容

我们的最终目标是一个大圆，当前需要讨论决定的是其中的小圆，即最小闭环。大圆用于指引最终目标，防止跑偏，而我们主要的讨论集中在当前小圆：终点、边界、验收。

**当发现待确认的问题太多，说明圆切大了。** 应当停下重切，而不是把问题逐条问完。这是本 skill 与穷举式评审的关键区别。

开始时，请先查清起点，也就是当前项目的状态。相关代码、文档、配置与现有状态调研到能下结论为止，然后压成几条已核实的事实请人核对，不要问当前是什么样。

给出大圆的一句话复述，并提出当前小圆：这一圈跑通什么，明确不做什么。常规细节按项目惯例先定默认方案一并列出，未否决即生效；只有真正难返工的选择才提出来，同时把验收确定下来。契约写完即停，用户认可再动工。

边界即明确不做的事，负向边界往往比正向描述更能避免执行期的顺手一做，导致的小圆变大圆。

验收分两类。可自动化的对齐小而全的测试集，一两条主路径加最关键的边界，附一条校验命令。不可自动化的对齐参考作品、核心偏好与红线，用原型来让用户判断，而不是泛泛而谈，用形容词或抽象词汇讨论。

当用户对概念不熟，可进行 `loop-teach`，学完再回来，不在讨论里展开。

## 契约文档模板

对齐后输出单页到 `docs/plan`：最终目标是一个文件夹，最小闭环是其中按序编号的一页，如 `docs/plan/20260606-实现skill评估框架/1-初始化开发环境.md`。目录不存在时自行创建；创建不了就近落盘，并在契约里写明位置。

无关项省略：

```markdown
# 闭环契约：<任务名>

## 最终目标
<一句话定义最终目标，只用于防跑偏>

## 起点
* <已核实的现状>

## 最小闭环
* 终点：<跑通后具备的能力或产出>
* 边界：<明确排除的延展项>

## 实现方案与讨论内容
* <按惯例先定的细节与讨论的内容与决策>

## 验收
* 自动化：<校验命令、主路径、关键边界>
* 人工：<参考作品、偏好、红线、验证方式>

## 关键路径
1. <核心改动点与自检步骤>
```

这份契约是 `loop-iterate` 复盘的对照基准，复盘追加在同一页末尾。
